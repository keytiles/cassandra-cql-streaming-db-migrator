## Why are we doing this?

- Large table migrations abort mid-stream on transient Cassandra/Scylla `ReadTimeoutException` during next-page fetch.
- Failure surfaces on `rowsIterator.hasNext()` because that is where `MultiPageResultSet` fetches the next page — not because `hasNext()` itself is conceptually wrong.
- Aborting after millions of rows already migrated is very costly, especially for counter tables where a naive full-query restart is unsafe (counter updates are not idempotent).
- Current write path already has `writeRetryStrategy`; reads have no equivalent resume/retry unit.

## What will be changed?

- Replace auto-iterated `ResultSet` paging with **manual page fetch** using driver paging state (`setPagingState` + consume only the current page via `getAvailableWithoutFetching()` / `one()`).
- Make the **driver page** the unit of retry, write completion, metrics, and optional pause.
- Add configurable **`readRetryStrategy`** (default on) and **`pageSizeReduceStrategy`** (reduce page size after read retries exhausted, bounded by `maxIteration`).
- Remove misleading `rowsRead % pageSize` "page exhausted" heuristic used for metrics/pause.
- Simplify/remove the streaming `rowsProcessBatchSize` accumulator from the read loop; keep filter `maxRowsBatchSize` as optional post-page chunking only.
- Update example config, Javadoc, and `CHANGELOG.md`.

## Decisions we made

- **Do not** wrap `hasNext()` in try/catch and retry the same iterator — iterator state after a failed page fetch is not a reliable resume API.
- **Do** retry by re-executing the same read query with the **same paging state** (failed page as retry unit).
- Continuous paging is a red herring for this failure: stack shows ordinary `MultiPageResultSet` from `session.execute()` + iteration. Configuring `CONTINUOUS_PAGING_*` options is not the root cause to "turn off" as the main fix.
- `rowsRead % pageSize` must not be treated as a real driver page boundary (metrics/pause only; dangerous if used for control flow).
- `migrateFetchedRows()` is not inherently batch-size sensitive; historical `rowsProcessBatchSize` mainly existed to respect filter `maxRowsBatchSize` (e.g. future `IfNotExistFilter` IN-query cost). That concern stays as **chunking after a page is fetched**, not as a second pacing loop interleaved with reading.
- For **counter tables**: page-level read retry is safe only if page N is fully written before attempting page N+1, and we never restart the full `SELECT` from scratch after partial success (would double-count). Existing write-timeout caution in `isSafeToDoWriteRetry()` remains.
- **`readRetryStrategy` is on by default** (retryCount=1, pause 3s, x2). Kept short because `pageSizeReduceStrategy` can then shrink the page. `writeRetryStrategy` stays opt-in. Set `retryCount: 0` to disable read retries.
- **Page-size reduce ladder** (after read retries for a page are exhausted): same query + same paging state, but smaller `pageSize`. Driver allows changing page size when resuming from paging state. Configured via `PageSizeReduceStrategy` next to `readRetryStrategy`. `maxIteration` caps how many reductions can occur across the **whole table migration** (default 4).
- Implement **step by step** so each step can be reviewed before the next.

## Implementation steps

### Step 1 — Manual paging (structure only, no retry yet) — **implemented**

- Replace `result.iterator()` / `hasNext()` auto-paging loop with explicit page processing:
  - execute query (optionally with paging state)
  - consume only the current page (`getAvailableWithoutFetching()` + `one()`; not `iterator()`/`all()`)
  - capture `ExecutionInfo.getPagingState()`
  - continue until paging state is null / no more pages
- Move page-fetch metrics and `pauseMillisBetweenPages` to **after a real page** is processed.
- Remove `rowsRead % pageSize` heuristic.
- Keep write behavior via `migrateFetchedRows()` for now (behavior should remain equivalent for typical configs where process batch ~= page size).
- Done in `MigrateTableTask.run()`: `query.setPagingState(...)` + page-local consume via `getAvailableWithoutFetching()` / `one()` (driver 4.12 sync API has no `currentPage()`); page-fetch histogram now measures only `session.execute()` time.

### Step 2 — Read retry on page fetch — **implemented**

- Add `readRetryStrategy` on `TableMigrationDefinition` (reuse `RetryStrategy` model).
- On read/page-fetch failures (at least `ReadTimeoutException`; classify similarly to write retries as needed):
  - retry the **same** query + paging state
  - apply pause / exponential backoff from strategy
  - if retries exhausted, fail the table task (current overall failure semantics)
- Do not re-process already completed earlier pages.
- Done: `MigrateTableTask.fetchNextPage()` + `isRetryableReadFailure()`; retries `ReadTimeoutException`, `UnavailableException`, `NoNodeAvailableException`, and other `*timeout*` failures. Default: `new RetryStrategy(1, 3000, 2)`.

### Step 3 — Page-size reduce after read retries exhausted — **implemented**

- New model `PageSizeReduceStrategy` (sibling of `RetryStrategy`):
  - `reducePageSizeFactor` (default `2`) — integer divisor applied to current effective page size
  - `maxIteration` (default `4`) — apply the reduce factor at most this many times for the **whole table migration** (do **not** keep dividing down to 1)
- Field on `TableMigrationDefinition`: `pageSizeReduceStrategy` next to `readRetryStrategy` (default instance enabled, same spirit as default read retry).
- Ladder for one page fetch:
  1. Try current effective `pageSize` with full `readRetryStrategy`
  2. If still failing with retryable error and global reduce iterations left → `pageSize = pageSize / reducePageSizeFactor` (integer division; stop if result would be `< 1` or unchanged), reset read-retry counter, same paging state
  3. Repeat until success, or `maxIteration` / no further meaningful reduce → fail table task
- After a successful reduced fetch, **keep** the reduced effective page size for subsequent pages (simpler; cluster was under stress). Optional “climb back up” is out of scope.
- Disable: set `maxIteration: 0`.
- Done: `PageSizeReduceStrategy`, `effectivePageSize` + `tryReduceEffectivePageSize()` in `MigrateTableTask`.

### Step 4 — Clean up batch-size complexity — **implemented**

- Drop streaming `rowsFetched` accumulation driven by `rowsProcessBatchSize` from the read loop.
- Process one driver page at a time; if filters declare `maxRowsBatchSize`, split that page into chunks for filter + write.
- Simplify/remove `RowFilters.rowsProcessBatchSize` as a read-loop concept.
- Done: `RowFilters` now holds optional `maxRowsBatchSize` (min of filter limits, or null = full page); `migratePageRows()` chunks only when needed.

### Step 5 — Docs / example config / changelog — **implemented**

- Document `readRetryStrategy` and `pageSizeReduceStrategy` in `config/migration-config.example.yaml` and relevant Javadoc.
- Update global `CHANGELOG.md`.
- Note counter-safety implication: resume via paging state only; never full-query restart after partial counter writes.
- Done: `docs/feature-MigrateTableTask-v1.1.md` (self-contained how-it-works); example YAML comments link to the doc; CHANGELOG already covered under 1.2.0.

## Notes / how to test

- Re-run a large counter migration similar to `migrate-byhitsourcecounters.yaml` (or a smaller `whereClause` slice first).
- Optionally lower timeouts / stress source briefly to provoke page-fetch timeouts and confirm:
  - retries appear in logs
  - migration continues from the failed page
  - row counts progress without restarting from zero
- Sanity-check with a filter that sets `maxRowsBatchSize` smaller than `pageSize` after Step 3.
- Ops still matter: smaller `pageSize`, higher `readQueryTimeoutMillis`, and/or `pauseMillisBetweenPages` reduce how often timeouts happen — they complement, not replace, resume logic.

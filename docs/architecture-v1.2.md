## TLDR

This is a **standalone Java 8 CLI jar** that streams table data from a Cassandra CQL–compatible source (Cassandra, ScyllaDB, …) into a target keyspace/table using the DataStax Java driver.

The operator supplies a **YAML config** (`-configYaml`), typically under `nohup` for long runs. The process:

1. Opens source and target CQL sessions.
2. Builds one migration task per configured table entry (after expanding any `variables` templates).
3. Prints the task list and requires start confirmation (`Y`/`N`, or `-y` for unattended).
4. Runs those tasks on a worker pool (`threadCount` — parallelism across *tables*, not within a table’s read stream).
5. For each table: page-read from source → optional row filters → write to target (via a pluggable migrator).
6. Logs periodic status and a final per-task summary, then exits.

Schema DDL is **not** migrated — tables must already exist. The tool moves **row data** (optionally filtered / transformed).

## How the operator starts it

Typical long-running invocation:

```bash
nohup java -jar ~/db-migration/cassandra-cql-streaming-db-migrator-1.2.0.jar \
  -configYaml migrate-normalcounters.yaml \
  -y \
  > migrate-normalcounters.log 2>&1 &
```

- Entry point: `com.keytiles.db_migration.Main`
- Required CLI flag: `-configYaml <path>` (Apache Commons CLI)
- Unattended / `nohup`: also pass `-y` / `--yes` (skip interactive start confirmation)
- Config is deserialized with Jackson YAML into `Config` (`Config.parseFromYamlFile`)

See [config/migration-config.example.yaml](../config/migration-config.example.yaml) and the operator guides under `/docs-user` ([how-to-start-migration-v1.0.md](../docs-user/how-to-start-migration-v1.0.md), [config-guide-v1.0.md](../docs-user/config-guide-v1.0.md)). Javadoc on `model.config` covers field-level details.

## High-level component map

```
Main
  └─ Config (YAML)
       └─ DbMigrator
            ├─ CassandraConnectionAdapter  (sourceDB)
            ├─ CassandraConnectionAdapter  (targetDB)
            └─ MigrateTableTask × N   (one per tables[] entry)
                 ├─ IRowSetFilter(s)       (optional chain)
                 ├─ IMigratorPlugin          (read query + per-row write)
                 └─ WriteRowTask pool        (parallelWriteRowCount)
```

- **`Main`** — CLI parse, load config, call `DbMigrator.migrate()`
- **Config** / **template expand** — YAML → optional `variables` cartesian expand → `TableMigrationDefinition` list
- **`DbMigrator`** — open connections, name tasks, confirm start, create/schedule tasks, wait, print finals, close
- **`CassandraConnectionAdapter`** — driver session lifecycle, timeouts, keyspace, metrics hook
- **`MigrateTableTask`** — one table’s streaming migrate loop (`Runnable`)
- **`IMigratorPlugin` / `DefaultMigratorPlugin`** — build SELECT; map/write each row (TTL, calculated cols, IF NOT EXISTS, …)
- **`IRowSetFilter` / built-ins** — in-memory (or DB-assisted) filtering before write

## Config model (operator contract)

Top-level `Config`:

- **`sourceDB` / `targetDB`** — keyspace, contact nodes, datacenter, optional request/paging timeouts. Target may be the same cluster when migrating between tables (`targetTableName`).
- **`threadCount`** — how many table migrations run in parallel. Keep `1` if later table entries depend on earlier ones.
- **`printStatusEveryXSeconds`** — status log cadence.
- **`tables`** — ordered list of `TableMigrationDefinition` entries.

Each table entry controls scope (`whereClause`, max row caps), pacing (`pageSize`, pauses), write concurrency, simulation, error policy, retries, optional filters, and optional custom migrator plugin. Defaults lean safe (e.g. `simulateOnly` defaults to `true` on the model — set explicitly in YAML for real runs).

Exact field semantics: Javadoc on `TableMigrationDefinition` and the example YAML. Resilience knobs for page reads: [feature-MigrateTableTask-v1.1.md](feature-MigrateTableTask-v1.1.md).

## Execution model

### Orchestration (`DbMigrator`)

1. Connect source and target via `CassandraConnectionAdapter`.
2. Construct one `MigrateTableTask` per `tables` entry (fail-fast if any task fails init / schema discovery).
3. Schedule all tasks on a fixed pool of size `threadCount` (tasks still start in config order; concurrency depends on free workers).
4. Poll until every task reports finished; shut down the pool.
5. Log per-task success/failure, durations, row counters, and warnings.
6. Close both connections.

### Per-table pipeline (`MigrateTableTask`) — overview only

Each task owns one table migration:

1. **Init** — resolve source/target `TableMetadata`; instantiate filters + migrator plugin.
2. **Read** — plugin supplies the SELECT; task fetches pages with **manual paging state** (not blind `ResultSet` iteration).
3. **Filter** — optional `IRowSetFilter` chain; may split a page by `maxRowsBatchSize`.
4. **Write** — each passing row becomes a `WriteRowTask` on a per-table write pool (`parallelWriteRowCount`); plugin performs the actual INSERT/UPSERT (or skips writes in simulate mode).
5. **Advance** — only after the current page is handled; optional pause; periodic status metrics.

Read retries / page-size reduction, write retries, and counter-table safety are documented in the MigrateTableTask feature doc — not repeated here.

## Extension points

The tool is intentionally pluggable via `com.keytiles.db_migration.api`:

- **`IMigratorPlugin`** — builds the read query and migrates one row. Default: `DefaultMigratorPlugin` (schema-aware column mapping, optional TTL, optional MVEL `calculatedColumns`, `insertOnlyIfNotExist`, counter-aware writes).
- **`IRowSetFilter`** — filters a batch of rows before write. Built-ins include `FieldValueFilter` (MVEL over row fields) and `IfNotExistFilter` (when INSERT IF NOT EXISTS is unsuitable).

Configured in YAML under `migratorPluginDefinition` and `dataFilterDefinitions` (class name + options map). Custom implementations can be dropped on the classpath.

## What this tool does *not* do

- Create or alter keyspaces/tables (DDL).
- Guarantee a single global transaction across tables.
- Replace cluster-level snapshot/restore tooling — it is a **CQL streaming row migrator** for controlled, observable, tunable data moves (including cross-table / filtered / simulated dry-runs).

## What changed vs previous

This is the first `/docs` version for `MigrateTableTask` (v1.1). Compared to the pre-1.2.0 behavior:

- Source reads use **manual paging** (driver paging state) instead of auto-iterating `ResultSet` (where `hasNext()` could throw on next-page fetch and abort the whole run).
- Default **`readRetryStrategy`** retries a failed page fetch with the same paging state.
- Default **`pageSizeReduceStrategy`** can shrink effective page size after read retries are exhausted (capped; does not grind down to 1).
- Filter/write batching is no longer tied to `pageSize` as a second pacing loop: each **driver page** is processed as a unit; optional filter `maxRowsBatchSize` only splits that page when needed.
- Write-side `writeRetryStrategy` (opt-in) and counter-safe write-timeout policy remain as before.

Also tracked in root [CHANGELOG.md](../CHANGELOG.md) under release 1.2.0.

## TLDR

One `MigrateTableTask` migrates **one** configured table (source → target). It:

1. Builds the source SELECT (via migrator plugin) with configured `pageSize` / timeouts / optional `whereClause`.
2. Fetches pages **explicitly** using paging state.
3. On read failure: retry same page (`readRetryStrategy`), then optionally reduce page size (`pageSizeReduceStrategy`).
4. Filters and writes the page (optionally in filter-sized chunks), with parallel writers and optional `writeRetryStrategy`.
5. Advances to the next paging state only after the current page was handled.

## Role in the tool

- `DbMigrator` schedules table definitions on worker threads (`threadCount`).
- Each worker runs one `MigrateTableTask` (`Runnable`) for one `TableMigrationDefinition`.
- The task owns its own write thread pool (`parallelWriteRowCount`).

## End-to-end flow (one table)

### Init

- Resolve source/target table metadata in the configured keyspaces.
- Require `continueOnRowError` to be set explicitly.
- Create row-set filters (if any) and the migrator plugin (default: `DefaultMigratorPlugin`).
- Validate `writeRetryStrategy`, `readRetryStrategy`, `pageSizeReduceStrategy` when present.

### Read loop (manual paging)

For each page until done or `maxWriteRowCount` reached:

1. **Fetch page** — `session.execute(query.setPageSize(effectivePageSize).setPagingState(...))`.
2. **Consume current page only** — `getAvailableWithoutFetching()` + `one()` (do not use `iterator()` / `all()`, which auto-fetch the next page).
3. **Migrate page** — see filter/write below.
4. **Take next paging state** — stop when null.
5. Optional `pauseMillisBetweenPages`, periodic status logs.

`effectivePageSize` starts as configured `pageSize` and may shrink via `pageSizeReduceStrategy`; once reduced it stays reduced for later pages.

### Read failure ladder

When a page fetch fails with a **retryable** error (`ReadTimeoutException`, `UnavailableException`, `NoNodeAvailableException`, or other `*timeout*`):

1. Apply **`readRetryStrategy`** (same query + same paging state, exponential pause).
2. If still failing and reduce iterations remain: apply **`pageSizeReduceStrategy`** — `effectivePageSize /= reducePageSizeFactor`, reset read-retry budget, retry same paging state.
3. If reduce is exhausted / cannot shrink further / error is non-retryable: fail the table task.

Defaults (when omitted from YAML):

- `readRetryStrategy`: retryCount=1, pauseMillisBetweenRetries=3000, exponentialPauseMultiplier=2 (one 3s wait before the last attempt). Disable with `retryCount: 0`.
- `pageSizeReduceStrategy`: reducePageSizeFactor=2, maxIteration=4 (e.g. 1000 → 500 → 250 → 125 → 62). Disable with `maxIteration: 0`.
- `maxIteration` is a **global** cap for the whole table migration (not unlimited per page).

### Filter + write (per page)

- Default: process the **whole page** in one `migrateFetchedRows` call.
- If any filter defines `maxRowsBatchSize`, the page is split into chunks of the **minimum** configured limit before filter + write.
- Filters run in config order; rows that pass are written via `WriteRowTask` on the write pool.
- **`writeRetryStrategy`** (optional): retries failed row writes with backoff. On **counter** target tables, timeout-like failures are treated as unsafe to retry (avoid double increments).
- `continueOnRowError`: if false, a failed row aborts the table migration; if true, count as failed and continue.

### Simulation

- `simulateOnly: true` (default on the config model for safety): same path except the actual UPSERT/INSERT execution is skipped.

## Counter-table safety

- Counter updates are **not idempotent**.
- Page-level **read** retry / page-size reduce is safe because the failed page has not been written yet; resume uses the same paging state (do not restart the full SELECT from scratch after partial success).
- Page N is fully handled before page N+1 is fetched.
- Write timeouts on counters remain conservative (no blind write retry on timeout).

## Main config knobs (table level)

See also `config/migration-config.example.yaml` and Javadoc on `TableMigrationDefinition`.

- **Paging / load**: `pageSize`, `readQueryTimeoutMillis`, `pauseMillisBetweenPages`
- **Read resilience**: `readRetryStrategy`, `pageSizeReduceStrategy`
- **Writes**: `parallelWriteRowCount`, `writeQueryTimeoutMillis`, `writeRetryStrategy`, `continueOnRowError`
- **Scope**: `whereClause`, `maxReadRowCount`, `maxWriteRowCount`, `simulateOnly`
- **Filters**: `dataFilterDefinitions` (+ optional `maxRowsBatchSize` per filter)
- **Plugin**: `migratorPluginDefinition` (default `DefaultMigratorPlugin`)

DB-level timeouts (`sourceDB` / `targetDB`: `requestTimeoutMillis`, `firstPageTimeoutMillis`, `followingPagesTimeoutMillis`) still matter; smaller pages and pauses reduce how often timeouts happen — they complement, not replace, resume logic.

## Status / metrics

Periodic logs include rows read / filtered / migrated / failed, time in read vs write, mean page-fetch and write-batch durations, effective page size (and configured size if reduced), and filter batch size (`n/a (full page)` when unlimited).
